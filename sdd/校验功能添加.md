# 餐饮系统 Agent 架构功能适配与决策评估

这份评估报告旨在梳理主流 Agent 底层能力在餐饮项目（KDS 联动、智能置换、审批流）中的具体应用映射，辅助研发团队决定一期（MVP）版本中是否引入这些功能。

---

## 1. Skill / Tool Calling (工具与外部系统调用)

*   **项目映射**：**全场景**的基础支撑。
    *   **场景 1 (KDS联动)**：调用 `queryKdsStatus()`, `suspendKdsTask()`。
    *   **场景 2 (智能置换)**：调用 `getSurplusInventory()` 查询剩余甜点。
    *   **场景 3 (审批流)**：调用 `updateOrderStatus()`, `addGiftToOrder()`。
*   **技术栈依赖**：Spring AI 或 LangChain4j 的 `@Tool` 注解，现有的 RESTful/RPC 接口。
*   **落地难度**：⭐️⭐️ (极低)
*   **决策建议**：🔥 **必须采用 (Must-have)**。这是大模型从“聊天机器人”转变为“智能体”的唯一途径。没有 Tool Calling，Agent 无法对您的数据库和打印机产生任何实际影响。

## 2. Context Management (上下文与状态持久化)

*   **项目映射**：**跨时间周期的状态维持**。
    *   **场景 1**：记住用户“推迟半小时”对应的原订单 ID 和原定时间。
    *   **场景 3 (最关键)**：订单在 LangGraph 节点挂起（Pending_Approval）时，必须将当前的图状态（Graph State，包含订单详情、意图识别结果）序列化保存。当店长在 10 分钟后点击“同意”时，系统需要从这里恢复上下文，继续向下执行。
*   **技术栈依赖**：Redis、PostgreSQL (LangGraph 的 Checkpointer 机制)。
*   **落地难度**：⭐️⭐️⭐️ (中等，需处理分布式状态)
*   **决策建议**：🔥 **必须采用 (Must-have)**。如果您的后端是分布式/无状态的微服务，且存在“人在环路”这种异步审批等待，脱离了基于持久化的 Context 管理，审批唤醒后 Agent 将彻底丢失之前的分析逻辑。

## 3. Sub-Agent / Multi-Agent (多智能体路由)

*   **项目映射**：**复杂逻辑解耦与防幻觉**。
    *   **场景 3**：拆分为“意图识别 Agent”（只负责看懂用户是不是在要赠品，输出 Boolean）和“执行 Agent”（负责修改订单）。
    *   **场景 2**：“库存查询数据 Agent” 和“逼单话术生成 Agent”。
*   **技术栈依赖**：LangGraph 的多节点 (Node) 编排与路由 (Conditional Edges)。
*   **落地难度**：⭐️⭐️⭐️ (中等，需设计良好的 State 数据结构)
*   **决策建议**：✅ **推荐采用 (Should-have)**。虽然您可以把所有系统提示词（Prompt）塞进一个巨大的 Agent 里，但随着业务变复杂，大模型很容易“忘记”某条规则。通过 LangGraph 将其拆分为 Sub-Agent，每个节点各司其职，能极大提高成功率并降低单次调用的 Token 消耗。

## 4. Human-in-the-loop (人在环路中断与唤醒)

*   **项目映射**：**场景 3 (店长审批流)** 的核心机制。
*   **技术栈依赖**：LangGraph 的 `interrupt_before` 或 `interrupt_after` API，WebSockets/长轮询 (用于C端和B端的通知)。
*   **落地难度**：⭐️⭐️⭐️⭐️ (较高，涉及前后端异步通信机制)
*   **决策建议**：✅ **按需采用 (根据一期资源决定)**。这是最体现业务价值的高级功能。如果一期开发资源紧张，可以先让 Agent 做“自动打标签（索要赠品）”，后台以传统的审批流完成；如果资源充足，直接引入 LangGraph 的图中断机制，实现原生的智能体挂起与唤醒，架构会极其优雅。

## 5. RAG (检索增强生成)

*   **项目映射**：结合您的当前需求，直接应用场景较少。
    *   *潜在扩充*：如果店长需要应对复杂的客诉（“菜里有虫子怎么赔偿”），可以结合 RAG 检索门店的标准操作程序（SOP）文档来生成应对方案。
*   **技术栈依赖**：向量数据库（如 pgvector、Milvus）、文本 Embedding 模型。
*   **落地难度**：⭐️⭐️⭐️ (需要额外维护数据管道)
*   **决策建议**：❌ **暂不推荐 (Skip for MVP)**。您目前的三个核心场景（KDS修改、查库存、判断备注意图）高度依赖结构化数据和明确的业务接口，属于逻辑分析和工具调用范畴，暂时不需要引入复杂的非结构化文档检索。

## 6. Sandbox (沙箱执行环境)

*   **项目映射**：防止 Agent 乱执行操作。
*   **决策建议**：❌ **完全不需要 (Not needed)**。您不需要 Agent 动态生成和执行 Python/JS 代码。Agent 的操作边界完全被限制在您提供的 RESTful API (Tools) 内。您只需要用传统的微服务网关、JWT 鉴权、接口限流（Rate Limit）来保护您的 `queryKdsStatus` 或 `addGiftToOrder` 接口即可，无需引入沉重的容器沙箱机制。
